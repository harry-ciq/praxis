# Tech Stack

Praxis is a full-stack application with a Go API server and a Next.js frontend. The backend handles business logic, auth, and real-time communication; the frontend renders a rich SPA with server-side rendering where it matters.

## Core

| Layer | Choice | Rationale |
|---|---|---|
| Frontend framework | **Next.js 16** (App Router) | SSR + client components, file-based routing, Turbopack for fast dev |
| Language (frontend) | TypeScript (strict) | Type safety end-to-end |
| Styling | **Tailwind CSS v4** + shadcn/ui | Utility-first CSS, consistent design system, zero runtime |
| Server state | **TanStack Query** | Caching, background refetching, optimistic updates |
| Backend framework | **Go 1.22+** with Chi router | Fast, type-safe, minimal dependencies, excellent concurrency |
| Database | **PostgreSQL 16** | Relational data with JSONB for flexible fields (achievement metadata, job requirements) |
| Cache / Queue | **Redis 7** | Session store, token blacklist, job queue backend, WebSocket pub/sub |
| Real-time | **gorilla/websocket** | WebSocket hub pattern for messaging and notifications |
| Auth | JWT (access + refresh) | Stateless auth with Redis-backed token invalidation |

## Frontend Detail

- **Next.js 16** with App Router — `use(params)` pattern for async params, React 19
- **shadcn/ui** with Base UI primitives (`@base-ui/react`) — accessible, unstyled components customized with Tailwind
- **TanStack Query** — all API calls go through a typed `ApiClient` wrapper; query keys are user-scoped to prevent cache pollution
- **Custom WebSocket client** — singleton `SocketClient` with auto-reconnect, event routing via handler map; `useSocket` hook at layout level for persistent connection
- **Editorial typography** — Geist for body, Geist Mono for code, **Playfair Display** as the editorial serif used by the Smart Feed hero stat, headline, and pull-quote highlight

## Backend Detail

- **Chi router** — lightweight, composable middleware, stdlib-compatible
- **pgx** (`jackc/pgx/v5`) for database access — raw queries in repository structs, no ORM, full control over the SQL we ship
- **golang-migrate** for database migrations — plain SQL files, up/down
- **go-chi/httprate** — global 100 req/min IP limiter, tighter 20 req/min on `/auth`, 10 req/min on `/feed/smart` (LLM call costs real tokens)
- **godotenv** with `Overload` (not `Load`) so `.env` wins over shell-exported vars — important for desktop launchers that export their own defaults
- **Zap** for structured logging — JSON in production, pretty-print in dev
- **WebSocket Hub** — goroutine-based hub with per-user client maps, broadcast channels, ping/pong keepalive
- **Asynq** task queue (Redis-backed) with three priority lanes (critical / default / low) and an in-process scheduler that enqueues `provider:sync` for every connected provider every `SYNC_INTERVAL_HOURS`

## Data

- **PostgreSQL** — primary data store for users, achievements, conversations, jobs, notifications
- **Redis** — JWT refresh token storage, rate limiting, background job queue (Asynq)
- Schema supports JSONB for achievement metadata and job requirements, enabling flexible matching without schema changes

## Infrastructure

- **Docker Compose** — PostgreSQL + Redis for local development
- **Air** — Go hot reload (watches `.go`, `.toml`, `.yaml`, `.sql` files)
- **Makefile** — `make dev` starts everything, `make test`, `make lint`, `make build`

## Provider Architecture

Achievement providers implement a common interface:

```go
type AchievementProvider interface {
    // ID returns a stable provider key (e.g. "GITHUB", "YOUTUBE").
    ID() string
    // Sync fetches the latest achievements for the given user/token. The
    // returned DetectedAchievement values carry a stable SourceID so the
    // service layer can deduplicate and archive across syncs.
    Sync(ctx context.Context, accessToken string, username string) ([]DetectedAchievement, error)
}
```

A `ProviderRegistry` maps provider IDs to implementations. **GitHub** and **YouTube** are both implemented today; new providers (LeetCode, Stack Overflow, npm, etc.) plug in by implementing the interface and registering themselves at server startup.

Each provider also exposes a small adapter interface (e.g. `GitHubAPI`, `YouTubeAPI`) so the unit tests can inject fake clients without hitting the network.

## AI / LLM (Smart Feed)

The Smart Feed digest is generated by Claude (Anthropic Messages API) and lives in `internal/llm` + `internal/service/smart_feed.go`.

- **Raw HTTP client**, no SDK. One endpoint, simple payload — keeps the dep tree small.
- **Prompt caching** — the system prompt is marked `cache_control: ephemeral` (`anthropic-beta: prompt-caching-2024-07-31`), so repeat calls within the 5-minute Anthropic cache window pay ~10% of the usual input-token price.
- **Per-user Redis cache** — generated digests are cached at `smart-feed:<userId>` with a configurable TTL (default 15 min). Cache is invalidated on follow/unfollow because the underlying feed scope changes.
- **Hallucination guards** — feed items sent to Claude include their real IDs; the parser drops any `achievementIds` Claude emits that don't match a real feed item, and any `targetUsername` that isn't actually present in the feed.
- **Graceful degradation** — when `ANTHROPIC_API_KEY` is unset the endpoint returns 503 and the UI shows a "Smart feed not configured" state instead of erroring.
- **Default model**: `claude-haiku-4-5` (cheap, fast). Override via `SMART_FEED_MODEL`.

## Testing & CI

- **Go**: handler / service / worker / provider / WebSocket-hub tests, run with `-race` in CI
- **Frontend**: Vitest + React Testing Library, currently 37 tests across achievement card, conversation list, reaction bar, job card, hooks
- **CI**: GitHub Actions at `.github/workflows/ci.yml`
  - **server** job: `vet` + `build` + `test -race`, with `postgres:16` and `redis:7` services
  - **web** job: `tsc --noEmit`, `npm run lint`, `npm test --run`, `next build`
- **Playwright e2e** is the next testing investment — Vitest covers component flows for now

## What We Are Not Using

- No GraphQL — REST is sufficient at this scale and keeps the API simple
- No ORM — pgx with hand-written SQL; full control, no magic
- No Docker images for production yet — local dev only; production deploy is Phase 26
- No cryptographic verification yet — `verification_hash` column exists but is unsigned. Phase 16 wires up Ed25519 signatures and a public verify endpoint
- No React Native — web-first; mobile is a Phase 27 consideration
